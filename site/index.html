Can these 100 apps become AI-agent toolkits today?

An agent pipeline researched auth, access gating, API surface and MCP availability for 100 apps across 10 categories. It then checked its own answers against live docs, fixed what failed, and re-checked. Every row links to its evidence. On a hand-checked sample, field accuracy moved from 78% (LLM first pass) to 95% (after the verification loops).

1. The patterns (headline)

  1. OAuth 2.0 dominates, but keys are the fast lane. 72/100 apps offer OAuth 2.0 and 23 are key/token-only. 55 of the 72 OAuth apps also issue a personal key or token, so a toolkit can ship on keys first and add OAuth for multi-tenant use. The OAuth-only ones include the app-review platforms (Google Ads, LinkedIn, Amazon, Pinterest, Threads) and accounting (QuickBooks, Xero).
  2. 73/100 are self-serve (57 free, 16 via free trial). The gates are concentrated. 8 need platform app review (WhatsApp Business, Google Ads, Meta Ads, LinkedIn Ads, Pinterest, Threads (Meta), Squarespace, Amazon Selling Partner). 8 are partner / contact-sales (DealCloud, Gladly, Salesforce Commerce Cloud, Waterfall.io, Clay, Paygent Connect, PitchBook, Consensus), and 11 need a paid plan.
  3. Openness tracks category. Fully open: Developer, Infra and Data platforms (10/10), Productivity and Project Management (10/10). Most gated: Marketing, Ads, Email and Social (5/10, mostly app review / approval), AI, Research and Media-native (5/10, mostly paid plan).
  4. The #1 blocker is commercial, not technical. Enterprise contract / customer account (14), Platform app review / approval (11), Paid plan required (7). Only 5 apps are truly blocked today; 63 are ready and 32 are buildable with a caveat.
  5. MCP is already mainstream. 73/100 apps ship an official MCP server and 14 more have community ones. Several gated or API-less products (Clay, Otter, DealCloud, iPayX) now expose MCP before, or instead of, a broad REST API.
  6. 63 easy wins vs 16 need outreach. Easy wins are self-serve, documented and verdict ready; outreach means partnership, app review or a contract.

3. The agent: what I built and where a human was needed

1. Draft (LLM)An LLM fills the schema for each app from its name and hint. Output is pass 1: fast, but unverified.
→
2. Crawl (agent)research.py fetches the docs, auth and homepage URLs and follows auth, pricing and MCP links. If HTTP fails or returns a JS shell, it falls back to headless Edge/Chrome, and every page is cached as evidence.
→
3. Cross-sourcemcp_check.py searches GitHub for MCP servers and marks vendor-owned repos as official.
→
4. Verify (agent)verify.py scores every claim as supported, unsupported, broken link or no evidence. It flags unclaimed auth methods, MCP mentions that pass 1 missed, and dead URLs.
→
5. Review (human-in-loop)inspect_evidence.py shows the snippet behind each flag. A reviewer accepts or rejects it, and accepted fixes go to corrections.json with before/after values and evidence. A stratified hand-checked sample measures true accuracy, and its misses become new verifier rules (loop 3).
→
6. Re-verify + buildCorrections are applied (pass 2), the verifier is re-run, and build_site.py computes every number on this page.

Where a human was needed

  • Judging flags. Keyword evidence is noisy. "OAuth" on Plaid's docs means bank-side OAuth, and Magento's "OAuth-based" means OAuth 1.0a. A reviewer rejected these and accepted real misses.
  • Dead and moved docs. LiveAgent, PitchBook, DealCloud and Ecwid needed a search for the new canonical URL.
  • Identity changes. fanbasis.com now redirects to Commas, and iPayX turned out to be an FX-audit engine, not a payment router. These were only caught by reading the rendered pages.
  • Access-model judgement. "Contact sales" on a marketing site doesn't mean the API is gated. Deciding self-serve vs partner needs reading, not regex.
  • Network realities. Corporate TLS inspection and bot walls (Meta 400, Salesforce 403) first looked like "broken links". The first verifier run penalised them wrongly, which is the reason for loop 2.

Run it

pip install -r requirements.txt
python agent/research.py            # crawl + evidence (browser fallback)
python agent/mcp_check.py           # GitHub MCP cross-check
python agent/verify.py data/pass1_llm.psv --label pass1
python agent/inspect_evidence.py 95 mcp   # review a flag
python agent/apply_corrections.py data/pass1_llm.psv data/pass2_verified.psv
python agent/verify.py data/pass2_verified.psv --label pass2
python agent/build_site.py          # -> site/index.html

Optional: python agent/research.py --llm re-derives every record from the cached evidence with any OpenAI-compatible model. This is the hook for swapping in Composio tools (web search, browser) as the agent's research actions.

Evidence-backed is the share of all claims where a fetched page contains a matching signal. Precision leaves out claims with no fetchable evidence. Both only score claims that were made, so they can't see omissions. A missed MCP server or OAuth flow makes no claim and can't fail. Omission flags count the cases where the docs show something the pass didn't claim. That's where pass 1 was weakest, and why the hand sample (right) is the headline accuracy number.
The first row is the very first run. Bot walls and corporate TLS made most failures crawler problems, not data problems (loop 1 fixed the crawler). Rows 2-3 judge both passes against the same final evidence. Loop 2 applied reviewed flag fixes, and loop 3 generalized the sample's misses into new rules. Hand-checked sample (20 apps, 2 per category)

A stratified random sample (seed 7, 2 apps per category). Each field was graded against the live docs: 1 = correct, 0 = wrong, blank = can't be confirmed without an account. 5. Where the agent was wrong, and what defeated it

  • Pass 1 was confidently stale. It got 28 MCP labels wrong (17 vendor servers missed entirely, 11 official ones labelled community) and 14 auth fields, missed Zendesk's deprecation of API tokens, and cited 5 moved URLs. An LLM's prior is a draft, not a finding.
  • Two apps were mis-identified (fanbasis is now Commas; iPayX is an FX audit engine), and Coda has rebranded as Superhuman Docs. Only rendering the live sites caught this.
  • The automated loop missed things the hand sample caught: Pipedrive and Meta Ads MCP, Harvest's trial, Zendesk auth and Otter access. 5 of the 20 sampled apps still had an error after loop 2. Generalizing those misses (loop 3) caught 7 more MCP misses across the other 80 apps, which suggests a similar residual rate outside the sample.
  • Keyword verification has a ceiling. It proves a word is on the page, not that the claim is right. For example, "OAuth" may refer to a different flow. That's why flags go to a reviewer, and why there is a separate hand-graded sample.
  • Access tier is the least certain field. Pricing pages are marketing-driven and change often. Treat paid vs trial as a lead to confirm before outreach.
  • Not fully verifiable without accounts. Ecwid's plan requirement for custom apps and Pylon/Grain API tiers are stated from docs, without signing up.
  • Some docs were unreachable from the network this ran on. A corporate web filter blocks some categories (messaging, "phishing"-classified hosts). These apps have no readable evidence and their rows are unverified, not confirmed: Pumble, Discord, Telegram. Re-running research.py on an open network fills them in. The crawler detects proxy block pages and discards them, so no proxy or user details end up in the evidence.
  • No paid accounts were used. Where an app is gated, the gate itself, with evidence, is the finding.
